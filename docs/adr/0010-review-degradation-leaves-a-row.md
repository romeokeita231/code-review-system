# 0010 审查降级必须落行，不能表现为缺席

- Status: Accepted
- Date: 2026-11-26
- Source: #51

## Context

写入后的审查 hook 抛错时，`src/entry/plugin.ts` 的 catch 只写错误日志，然后 fail-open，不追加任何记录。于是「这次写到底有没有被审阅」既没有肯定证据，也没有否定证据：读取端看到的只是一次写没有对应的审查行，与「没有写」不可区分。

这不是假设。ds-2 的 B4g 有 25 条写入前记录、20 条写入后记录，缺的正是最前面 5 次写（07:01:20–07:01:34）；同一批文件在 07:01:59 被重写后才补出后 5 条。本 run 里它们被后续重写覆盖，所以没有影响 line 3 计数，但证据链是断的。

ADR-0008 已经规定：可能由降级路径产生的观测，只能渲染为 `degraded` / `null` / `not_applicable`，不能表现为「什么都没发生」。审查行缺席正是「什么都没发生」的写法。

现有词汇里「降级」只指源超时或不可用，且绑定「降级来源不得产出机械阻断」。post hook 的失败是另一条路径：不是某个源降级，而是这次写根本没有审查结论。

契约上还有两个约束：审查记录没有用于「降级」的结果状态（结果状态是 `ok|partial|timeout|failed|unknown|skipped`，带 `degraded` 的是「审查是否完成」这一维）；工具身份首次探测要真跑二进制，错误路径里不能顺手再跑一遍。

## Decision

- 审查运行时已就绪后的 post hook 失败，必须追加一条审查记录，而不是只写日志。记录沿用现有审查记录的形状：审查状态为降级、结果为失败、写入后决策为未运行、来源与合并结果为空、工具身份取配置声明值（`source: "declared"`，明确表示没有活工具作答）、档位 0 / none。
- 原因记两处：固定的原因类别 `post_hook_failed` 用于汇总，另附一段截断后的具体错误文本用于排查。
- 不扩结果状态枚举；「降级」落在「审查是否完成」这一维。
- 汇总验收行时剔除降级记录。计数写入运行清单：总数、按基线计数，以及能归属到样本的 `(baseline, sample, ts)` 列表。旧 run 缺这一项时显示 `na`，不显示 0。
- line 3：受影响的 warned pair 记为未测到，line 3 不得通过，明细单列。分母口径不变。
- 覆盖边界：只覆盖运行时已就绪后的 post 失败。启动失败（没有 config、没有日志路径）、pre hook 失败、以及日志本身写不进去的失败，均记为已知缺口，只保留错误日志。
- 术语上新增「审查降级」，与源的「降级」分开。

## Consequences

- `review.jsonl` 会多出没有审查结论的行；`collect` 与成本统计必须跳过它们，否则 `tokens: null` 会污染「多少行没有 token」。
- line 3 会变严格：一次「写了但审不了」不再能被读成「被告知后不再动文件」或「已修好」，可能因此不通过。
- 启动失败与 pre hook 失败仍不可观测。要补上，需要另一张票，而不是在本票里顺手扩大范围。
